# 登录账号的数据隔离

2026-10-06 修复：旧版只校验用户是否加入 `CONTENT_FACTORY_WORKSPACE_ID`，但所有业务数据都写入该固定空间。同一部署内的不同邮箱会共享定位、资料和内容。

现在固定空间仅用于邀请资格校验。经 Supabase `getUser()` 验证且有邀请资格的用户，首次访问时由服务端建立独立 workspace：ID 由部署邀请 workspace 和该用户的 Auth UUID 确定，避免同一 Supabase 项目内不同部署或 Preview 的数据串用，并建立本人 owner membership。客户端提交的用户 ID、workspace ID 或请求头均不能选择数据归属。所有云端 JSON 仓库、数据库适配器通过同一个当前身份解析器访问个人空间；缺少云端存储配置时拒绝访问，不回退到共享本地文件。

后台建档启动时记录服务端验证的 workspace ID，并传给每一个 workflow step；step 用 AsyncLocalStorage 建立该次执行的数据上下文，因此用户离开页面、切换账号或同时执行另一账号的任务，不会改变写入归属。修复前启动且没有归属参数的旧云端任务会拒绝访问数据，需由所属用户重新提交。

采集插件的一键授权改为按账号签发的 HMAC token，有效期 30 天。每次采集仍核验该账号的邀请资格。原共享 token 在邮箱登录模式下失效，请重新点击采集授权；独立部署的 Basic Auth 模式保留原行为。

同一浏览器的本地知识索引和文件夹 handle 也按个人 workspace 分库；旧共享 IndexedDB 不自动读取或删除。登录成功后使用完整页面导航，重置原账号的页面缓存与内存状态。侧栏显示当前邮箱，便于核对身份。

## 旧数据

旧部署 workspace 的原始记录完整保留，修复不删除、不自动分配混合资料，也不复制到所有新用户。个人空间初始为空，需要分别重新确认定位、导入资料；本地文件夹重新授权。若需恢复旧数据，应先核对每条资料归属，再有选择地迁移。旧版未保存操作者，不能可靠地自动重建已被覆盖的定位。

## 验证

`node --test src/tests/account-isolation.test.mjs` 在生产构建上使用隔离的模拟 Supabase Auth、REST 数据库与 AI 服务，覆盖同一邀请空间内两用户同时保存定位、多次切换读取、伪造空间头、无资格用户、旧共享数据保护、已知他人草稿 ID、私有资料、采集 token 篡改和资格撤销，以及后台任务并行与原账号归属。模拟服务不使用生产凭据。
