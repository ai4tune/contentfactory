# 0. 文档使用说明

本文件是内容工厂第一版的技术规格说明，也是项目开发阶段的单一事实来源（Single Source of Truth）。

产品目标、用户流程、商业验证标准和功能优先级以 `docs/prd/Content-Factory-MVP-PRD-v0.1.md` 为上位依据；本文件负责把 PRD 转换为可实现、可测试的技术边界。如两者冲突，必须先修订 PRD 或本 Spec，不能由代码自行决定产品范围。

## 0.1 当前实施决策

V0.1 不以标准多租户 SaaS、漂亮后台或桌面安装程序作为起点，而采用：

```text
首次：插件采集账号 → AI 定位 → 保存当前唯一账号
日常：连接用户自有知识源 → 选择选题和资料 → 选择渠道
→ 生成统一内容简报 → 生成渠道内容 → AI 审核 → 人工修改 → 复制发布
```

当前默认实施约束：

1. 产品通过浏览器使用，不要求客户安装桌面程序；
2. 第一版不建设注册、成员、角色和复杂访问控制，真实客户采用独立部署或人工配置；
3. 本地文件夹中的 Markdown、TXT 是第一优先知识源；
4. 飞书知识库、飞书云文档作为企业知识源；
5. Obsidian / GitHub 用户优先读取本地克隆目录，GitHub 远程连接后置；
6. 原始企业知识优先保留在客户自己的知识源中；
7. 系统只保存当前账号定位、知识源元数据、选题、必要引用、内容简报、渠道草稿和审核结果；
8. 服务端不保存完整模型请求正文，不将客户全部知识复制为平台云盘；
9. AI 能力统一通过客户专属凭证访问 AI Gateway，并记录最小必要用量；
10. V0.1 的目标是验证“知识资料到可发布内容”的生产能力，而不是验证完整增长系统或 SaaS 平台能力；
11. 浏览器插件进入 P0，但只做用户主动打开页面后的可见信息采集；
12. 爆款采集、发布复盘和草稿箱推送均为 P1，不得阻塞 P0；
13. 第一版固定支持公众号文章、小红书笔记、朋友圈文案和短视频脚本四种内容；
14. 内容创作是默认首页，不建设独立数据看板作为第一入口；
15. 在首个付费验证前，允许使用本地 JSON、IndexedDB 或单实例轻量持久化，不强制引入 Postgres。

若后文章节仍出现多租户、Supabase Auth、RLS、桌面安装程序或完整 Obsidian 同步等设计，它们默认属于后续版本，不能覆盖本节的 V0.1 决策。

Codex 在实现本项目时，应优先遵循本文件中的：

1. 产品边界；
2. 页面与流程；
3. 数据模型；
4. 权限隔离；
5. API 设计；
6. AI 工作流；

8. Roadmap；
9. 非目标范围。

如文档与代码冲突，默认以本文件为准；如确需调整，应同步更新本文件。

# 1. 产品概述

## 1.1 产品名称

项目名称：**内容工厂（Content Factory）**

内部历史名称：**AI Growth OS / 企业 AI 内容增长系统**

第一版统一使用“内容工厂”，避免产品定位继续膨胀为完整增长操作系统。

## 1.2 一句话定位

帮助企业或个人把“账号定位 + 自有知识 + AI 生成”组合成一套可以持续产出多渠道内容的工作流程。

## 1.3 核心目标

V0.1 只解决四个问题：

- AI 不理解用户是谁、面向谁以及应该用什么风格表达；
- 企业或个人知识资料无法方便地进入内容生成上下文；
- 同一个选题改写为多个渠道内容耗时较长；
- AI 草稿事实不稳、AI 腔明显，需要大量人工重写。

## 1.4 核心价值

内容工厂 V0.1 通过以下链路帮助用户持续产出内容：

```text
账号定位
→ 选择选题
→ 选择企业或个人知识
→ 生成统一内容简报
→ 生成公众号 / 小红书 / 朋友圈 / 短视频脚本
→ AI 审核
→ 人工修改
→ 复制发布
```

## 1.5 目标客户

首批目标客户：

- 建材与家居企业；
- 汽车销售与汽车供应商；
- 本地生活服务企业；
- 咨询、猎头、教育培训等依赖内容获客的企业；
- 企业创始人个人 IP；
- 中小企业市场、销售或运营团队。

# 2. 产品原则

## 2.1 业务原则

1. 不承诺全自动获客；
2. 不承诺生成内容必然成为爆款；
3. 不以搬运、洗稿、规避平台检测作为核心能力；
4. 参考外部爆款时，只提取选题、结构、表达形式与用户关注点；
5. 企业事实、产品信息、案例与观点必须优先来自企业知识库；
6. 所有对外发布内容必须经过人工审核；
7. 以可追溯、可复盘、可持续优化为优先目标。

## 2.2 技术原则

1. Web 端为主系统，第一版限定桌面 Chrome / Edge；
2. V0.1 采用单实例、单账号，后续再评估多租户；
3. 客户原始知识归客户并优先保留在客户自有知识源；
4. 模型能力通过统一 AI Gateway 接入；
5. AI Provider 不写死；
6. 原始知识、账号采集数据、内容简报、渠道草稿和审核结果必须分开；
7. 所有 AI 输出必须保存模型、Prompt 版本、调用时间和状态；
8. 第一版优先可用性，不追求复杂自动化；
9. 插件采用用户主动打开页面后的引导式采集，不建设后台爬虫；
10. 本地文件夹作为默认知识源，飞书作为企业连接器，文件上传作为兜底，GitHub 远程连接后置；
11. V0.1 不建设自有企业文件云盘；
12. 知识只按当前任务需要读取，模型调用日志不得保存完整敏感正文。
13. V0.1 只跑通单账号：首次定位完成后保存为当前账号，选题和内容生成默认继承该定位；
14. 用户只有在业务方向发生变化时才主动“升级定位”，升级会更新当前账号，不新增第二个账号；
15. 爆款采集、远程 GitHub、草稿箱推送和发布复盘属于 P1；
16. V0.1 不建设向量数据库，先使用标题、标签、关键词和正文搜索，并由用户确认本次资料；
17. 四渠道内容共享统一内容简报，但必须使用独立渠道生成规则；
18. 内容审核与人工修改在结果页完成，不建设独立复杂审核中心。

# 3. 产品范围

## 3.1 V0.1 必做模块

1. Chrome 插件采集当前页面可见的账号、内容和指标；
2. 单账号定位分析、确认、保存和更新；
3. 无历史账号时的快速定位兜底；
4. 浏览器选择本地知识库文件夹；
5. Markdown、TXT 读取、搜索、预览和刷新；
6. 飞书文档、多维表格按需读取；
7. 本地 GitHub 克隆目录作为普通文件夹读取；
8. 手工输入选题和 AI 推荐选题；
9. 候选知识推荐与用户确认；
10. 统一内容简报；
11. 公众号文章、小红书笔记、朋友圈文案和短视频脚本多选生成；
12. AI 事实、风格和平台审核；
13. 人工编辑、单渠道重新生成、复制和 Markdown 下载；
14. 草稿历史与继续编辑；
15. AI Gateway 和最小调用记录。

## 3.2 V0.1 暂不做

1. 绕过登录、验证码或平台权限；
2. 大规模平台爬虫和完整历史账号监控；
3. 自动发布和推送平台草稿箱；
4. 自动私信；
5. 自动规避平台风控；
6. 手机墙、矩阵号批量操作；
7. 复杂 CRM；
8. 完整视频自动剪辑；
9. 实时评论监控；
10. 复杂工作流编排器；
11. 多 Agent 自主运行；
12. 多层级复杂审批流；
13. 标准多租户 SaaS、公共注册；
14. 企业成员和复杂角色权限；
15. 自有云盘与完整知识托管；
16. 桌面安装程序；
17. 后台持续监听或同步本地文件夹；
18. GitHub 远程连接和其他企业云盘；
19. 完整向量数据库与复杂 RAG；
20. 自助注册、付费和套餐后台；
21. 爆款采集与拆解；
22. 发布记录、指标复盘和运营周报；
23. 图片生成和视频剪辑；
24. 独立数据看板和复杂后台管理界面；
25. Word、PDF、图片和视频知识解析；
26. 四种核心渠道之外的大量内容形式。

# 4. 使用者与访问方式

## 4.1 V0.1 使用者

V0.1 面向杏仁本人和单个试点企业，由企业创始人、负责人或指定运营人员使用同一实例。

第一版不开发成员管理和复杂角色系统。实例只需要区分：

- 企业使用者：完成定位、知识连接、生成、审核和复制发布；
- 实施顾问：协助配置知识源、Prompt、账号定位和首批内容；
- 系统服务端：管理 AI Gateway 凭证、额度与异常，不读取无关企业知识。

## 4.2 V0.1 访问方式

第一版允许本地开发地址、客户专属网址或独立部署地址直接进入，不开发完整登录系统。

约束：

1. 不开放公共注册；
2. 不提供跨企业切换；
3. 真实企业资料仅用于其独立试点实例；
4. Provider Key 不向客户前端暴露；
5. 当应用公开部署或出现第二个真实客户时，再增加访问码或最小身份确认；
6. 飞书 OAuth 只在知识授权确有需要时增加，不作为 V0.1 登录前置条件。

## 4.3 后续角色模型

当出现真实的多人协作需求后，再增加平台管理员、企业管理员、运营、审核和只读角色。该角色模型属于标准 SaaS 阶段，不得阻塞 V0.1。

# 5. 企业实例与数据边界

## 5.1 基本原则

V0.1 每个真实试点企业使用独立实例或独立配置。首个付费验证前不强制使用独立数据库。

客户原始知识优先保存在飞书或 GitHub 等客户自有知识源；系统不建设自有企业文件云盘。

## 5.2 隔离对象

以下对象必须按企业实例隔离：

- 当前账号定位；
- 插件采集的必要账号证据；
- 知识源连接配置、文档标识和引用；
- 内容选题；
- 内容草稿；
- 草稿历史和修改版本；
- AI 调用记录；
- Prompt 配置；
- 客户专属 AI 凭证和用量。

## 5.3 数据库策略

V0.1 优先使用：

- 本地 JSON、浏览器 IndexedDB 或单实例轻量持久化；
- 本地目录句柄只保存在用户浏览器环境；
- 本地文件正文按需读取，不复制整个目录；
- 飞书连接信息和文档标识使用服务端配置；
- 不启用 Postgres、Drizzle、对象存储或 pgvector，除非 P0 真实使用暴露明确需要；
- 后续部署第二个真实客户或需要远程共享草稿时，再迁移到托管 Postgres。

## 5.4 隐私边界

系统必须做到：

- 仅在用户发起任务后读取必要知识；
- 界面展示本次使用的知识来源；
- 完整模型请求正文不写入普通日志；
- 临时上传原文件到期删除；
- AI Gateway 仅记录客户标识、模型、Token、耗时、状态和错误码；
- 敏感知识可标记为禁止发送给 AI；
- 后续合并为多租户 SaaS 时，再增加 `organization_id`、RLS 和角色权限。

# 7. 页面规格

# 7.1 内容创作页（默认首页）

功能：

- 展示当前账号定位摘要；
- 输入或选择选题；
- 搜索并确认本次使用的知识资料；
- 多选公众号、小红书、朋友圈、短视频脚本；
- 生成统一内容简报；
- 生成、切换和单独重试渠道内容；
- 显示引用来源和审核结果；
- 在线人工编辑、复制、下载和保存草稿。

验收标准：

- 用户不经过数据看板即可开始内容创作；
- 账号定位、目标客户和品牌语气自动继承；
- 没有连接知识源时给出明确引导；
- 没有账号定位时可以快速定位或先跳过；
- 用户可以只生成一个渠道，也可以生成全部四种渠道；
- Provider Key 和飞书密钥不得出现在前端。

---

# 7.2 当前账号页

展示：

- 插件采集入口和采集状态；
- 当前唯一账号；
- 定位、目标客户、核心产品；
- 内容支柱；
- 风格、常用表达和禁用表达；
- 下一阶段内容方向；
- 推荐选题；
- 分析依据和缺失信息；
- 更新定位入口。

## 7.2.1 单账号状态规则

- 一个企业实例只有一个当前账号；
- 首次定位保存后，定位页默认展示结果，不再展示完整问卷；
- 选题推荐自动读取目标人群、产品、平台和账号定位；
- 内容生成自动读取账号定位和目标人群；
- “升级定位”允许重新分析并覆盖当前结果；
- V0.1 不提供账号切换、账号列表和多账号统计；
- 无历史账号时允许通过企业资料快速建立初始定位；
- 插件只读取用户当前浏览器有权限看到的页面信息。

---

# 7.3 知识库页

功能：

- 用户主动选择本地知识库文件夹；
- 读取 Markdown、TXT 文件列表和正文；
- 连接并读取飞书文档或多维表格；
- 将本地 GitHub 克隆目录作为普通文件夹读取；
- 搜索、刷新和预览知识资料；
- 展示来源、更新时间和本次发送边界；
- 允许撤销本地目录授权或移除连接。

验收标准：

- 桌面 Chrome / Edge 可以由用户手势唤起目录选择；
- 未经用户授权不能读取本地文件；
- 本地文件变化后可手动刷新；
- 不默认上传或复制整个知识库；
- 飞书文档读取失败时给出权限或链接提示；
- 创作页可以搜索并选择已连接资料。

---

# 7.4 草稿历史页

展示：

- 选题；
- 创建时间和最后修改时间；
- 已生成渠道；
- 审核状态；
- 使用的知识来源数量；
- 继续编辑、复制和下载入口。

V0.1 不做发布指标、周报或复杂内容管理，只保证用户能找回并继续编辑生成内容。

# 8. 爆款采集箱

> 范围说明：本章保留为 P1 设计参考，不属于 V0.1 P0，也不作为内容创作前置条件。

## 8.1 目标

用户能够把外部高表现内容快速保存到系统，并由 AI 进行结构分析。

## 8.2 支持输入方式

P1 支持：

1. 粘贴链接；
2. 复制正文；
3. 上传截图；
4. 上传图片；
5. 上传视频；
6. 上传字幕；
7. 上传 PDF；
8. 手工录入互动数据。

后续增加：

- Chrome 插件；
- 批量导入；
- 视频自动转写；
- 页面截图；
- 可见文本采集。

## 8.3 采集字段

- 标题；
- 平台；
- 链接；
- 作者；
- 发布时间；
- 内容正文；
- 封面；
- 图片；
- 视频；

## 8.4 爆款库展示规则

爆款库默认先展示文章列表，而不是录入表单。每条列表至少显示：

- 标题、平台、来源关键词和录入时间；
- 原始互动数据；
- AI 摘要；
- 2～3 条可学习的核心点。

点击文章进入详情页，详情页分为两栏：

- 原文：标题、链接、原始正文或摘要、原始数据；
- 拆解：爆款原因、结构、可复用方法、适配当前账号的改写方向、风险提醒。

新增爆款通过独立的“录入并拆解”入口完成，成功后回到爆款详情。

# 11. 外部知识源集成

## 11.1 目标

允许客户继续在自己的知识工具中维护资料，Web 系统读取用户明确授权的本地目录或远程文档，并按任务需要使用。

## 11.2 V0.1 优先级

第一版按以下顺序支持：

```text
本地文件夹（Markdown / TXT）
→ 飞书云文档 / 知识库 / 多维表格
→ 本地 GitHub 克隆目录
→ 临时文本粘贴
```

GitHub 远程私有仓库连接、Word、PDF 和其他企业云盘属于 P1。V0.1 不做双向同步。

## 11.3 本地文件夹连接

通过浏览器 File System Access 能力：

1. 用户点击“选择知识库文件夹”；
2. 浏览器弹出目录选择和权限确认；
3. 前端保存目录句柄或必要授权状态；
4. 前端枚举支持格式的文件并建立轻量索引；
5. 用户刷新时重新读取文件修改时间和正文；
6. 只在生成任务中把用户确认的必要内容发送给服务端。

约束：

- 第一版限定桌面 Chrome / Edge；
- 必须由用户手势触发目录授权；
- 服务端不能主动读取用户磁盘路径；
- 换设备后用户需要重新选择同步到当地的文件夹；
- 文件夹跨设备同步由 GitHub、Obsidian Sync、iCloud、OneDrive 等外部工具负责。

## 11.4 飞书连接方式

通过飞书 OAuth 或企业自建应用授权：

1. 搜索当前用户有权访问的云文档或知识库；
2. 保存文档标识、标题、版本和更新时间；
3. 在内容任务中按需读取必要文档；
4. 展示知识引用；
5. 不默认复制整个知识库。

## 11.5 Obsidian + GitHub 方式

V0.1 中，Obsidian 用户将资料同步到私有 GitHub 仓库，并在当前电脑克隆后按本地文件夹读取。系统不需要 GitHub Token。

P1 再通过只读 GitHub App 或用户授权直接读取远程 Markdown。

Front Matter 示例：

```yaml
---
title: 强化地板产品介绍
type: product
tags:
  - 强化地板
  - 产品资料
public_for_content: true
updated_at: 2026-07-13
---
```

## 11.6 更新策略

V0.1 不回写客户知识源，因此不存在双向冲突。

系统根据来源标识、相对路径、版本、更新时间或内容哈希判断变化：

- 来源变化时刷新索引或缓存；
- 生成结果保留当时引用的来源标识；
- 临时上传文件按保留期限删除；
- 后续再评估完整增量同步和版本历史。

## 13.1 输入

## 13.2 内容形式

- 朋友圈文案；
- 短视频脚本。

用户可以只选择一种，也可以一键生成全部四种。其他内容形式属于 P1 或以后。

## 13.3 一次生成的“内容包”

一次任务输出：

1. 统一内容简报：目标受众、内容目标、核心观点、事实证据、结构、行动引导、引用和待确认信息；
2. 用户已选择渠道的内容；
3. 每种渠道的事实、风格和平台审核结果；
4. 用户人工修改后的最终版本。

渠道内容要求：

- 公众号文章：标题、摘要、完整正文；
- 小红书笔记：3～5 个标题、开头钩子、正文和话题建议；
- 朋友圈文案：个人化短文案和自然互动入口；
- 短视频脚本：前三秒钩子、口播正文、节奏或画面提示和结尾行动。

## 13.4 生成策略

```text
读取选题
→ 生成知识检索问题
→ 搜索本地文件夹或远程知识源
→ 用户确认候选资料
→ 组装证据包
→ 生成统一内容简报
→ 按已选渠道分别生成
→ 事实、风格和平台审核
→ 人工编辑
→ 保存、复制或下载
```

四个渠道 Prompt 必须独立。不得把同一篇正文只做长度调整后当作多渠道输出。

- 本地知识正文：按需读取，不上传保存整个副本；
- 飞书知识：保存连接配置和文档标识；
- 首个付费验证前不强制使用 Postgres、Drizzle 或 pgvector；
- 出现跨设备草稿同步、第二个客户或远程共享需求后，再迁移到托管 Postgres。

## 23.3 认证

- 本地开发和内部试用不做登录；
- 真实客户使用独立部署、访问码或人工配置；
- 飞书 OAuth 仅在知识授权需要时使用；
- 不开放公共注册；
- 标准 Auth、多成员和角色系统后置。

## 23.4 文件存储

- 企业原始知识：客户本地文件夹、飞书或本地 GitHub 克隆目录；
- 临时文本：只在任务内存中使用或按明确期限删除；
- 平台不建设永久企业文件云盘。

## 23.5 AI

- OmniRoute / 自有 AI Gateway；
- OpenAI-compatible API；
- 支持多模型切换。

## 23.6 部署

- 本地或 Vercel：Web；
- 本地 JSON / IndexedDB：首轮验证数据；
- 独立服务：AI Gateway；
- 真实客户使用独立实例或独立配置；
- 后续根据客户数量演进为标准多租户部署。

# 26. 关键工作流

## 26.1 首次账号定位

```text
用户安装或启用插件
→ 打开账号主页或创作者后台
→ 插件读取当前页面可见信息
→ 用户可补充采集代表性内容或后台数据
→ AI 生成定位、风格、内容方向和推荐选题
→ 用户确认或编辑
→ 覆盖保存当前唯一账号
```

## 26.2 内容生成

```text
输入或选择选题
→ 自动读取当前账号定位
→ 搜索本地文件夹或飞书知识
→ 用户确认候选资料
→ 生成统一内容简报
→ 用户选择一个或多个渠道
→ 按渠道生成内容
→ 事实、风格和平台审核
→ 人工修改
→ 保存、复制或下载 Markdown
```

## 26.3 本地知识读取

```text
用户点击选择知识库文件夹
→ 浏览器申请目录读取权限
→ 前端枚举 Markdown / TXT
→ 建立文件名、标签、正文轻量索引
→ 用户输入选题
→ 前端搜索候选资料
→ 用户确认
→ 只发送必要正文或片段
```

## 26.4 飞书知识读取

```text
用户连接或粘贴飞书文档
→ 保存授权和来源标识
→ 根据任务生成检索词
→ 搜索候选文档
→ 按需读取必要内容
→ 记录引用
→ 不回写客户知识源
```

## 26.5 P1 爆款与发布

```text
爆款采集与拆解 → 为选题和结构提供可选参考
审核完成 → 推送平台草稿箱 → 用户人工确认发布
发布后 → 记录数据 → 复盘内容方向
```

# 28. 非功能要求

## 28.1 性能

- 页面首屏加载 < 3 秒；
- 常规列表查询 < 1 秒；
- 本地目录首次索引和刷新必须显示进度；
- 内容简报、各渠道生成和 AI 审核分阶段显示状态；
- 只向 AI 发送用户确认的必要知识片段，超出上下文预算时先摘要或请用户缩小范围；
- V0.1 不处理图片、音频、视频等大型二进制知识文件。

## 28.2 安全

- 本地开发和内部试用不引入登录权限；真实客户通过独立部署、访问码或人工配置限定访问；
- 模型 Key 只存服务端；
- 不向前端暴露 Provider Key；
- 本地文件夹必须由用户主动选择并授予浏览器读取权限；
- 服务端不保存完整本地知识库副本；
- 日志不记录完整隐私内容；
- 飞书只申请读取指定知识来源所需的最小只读权限；
- GitHub 远程授权属于 P1，V0.1 优先读取用户本地克隆目录。

## 28.3 可观察性

需要记录：

- API 错误；
- AI 调用错误；
- 本地目录授权和索引错误；
- 飞书知识读取错误；
- 内容简报、渠道生成和 AI 审核失败的阶段、耗时和错误类型。

# 29. 商业模式与交付形态

V0.1 不是低价自助 SaaS，而是“账号定位 + 知识整理 + 多渠道内容生产”的实施型交付工具。

第一阶段建议交付包：

- 一次账号定位和内容风格确认；
- 第一批企业资料整理和知识源连接；
- 四渠道内容生成 Web 工具；
- 第一批真实选题和内容交付；
- 事实、风格和平台审核；

1. 真实资料能否转化为多渠道内容；
2. 内容是否经过少量修改即可发布；
3. 崔总是否愿意为这项能力支付约 3000 元。

# 33. V0.1 验收标准

产品验收：

- 用户可以通过插件采集当前页面可见账号信息；
- 用户可以确认、编辑并保存当前唯一账号定位；
- 用户可以在桌面 Chrome / Edge 选择本地知识库文件夹；
- 系统可以读取和搜索 Markdown、TXT；
- 用户可以连接飞书并查看系统实际引用的知识来源；
- 用户可以输入选题并确认本次使用的资料；
- 系统可以生成统一内容简报；
- 用户可以多选公众号、小红书、朋友圈和短视频脚本；
- 四种输出符合各自渠道结构，不是简单长度变化；
- 稿件可进行事实、风格和平台 AI 审核；
- 用户可人工编辑和审核；
- 用户可以单渠道重试、保存、复制和下载；
- 用户可以在草稿历史中继续编辑；
- 平台不长期保存客户全部原始知识，普通日志不包含完整正文。

业务验收：

- 输入一组真实资料，可以生成四种渠道内容；
- 生成内容经过少量修改即可发布，目标修改比例低于 30%；
- 一次完整生成流程目标在 10 分钟内完成；
- 杏仁本人连续一周真实使用并提高发布频率；
- 崔总认为内容能看、能改、能发；
- 崔总愿意为“知识整理 + 内容生产能力 + 首批内容交付”支付约 3000 元，或给出可验证的明确购买条件。

# 34. Codex 实施要求

Codex 在生成代码时必须遵守：

1. TypeScript strict mode；
2. 不允许使用 `any`，除非有明确注释；
3. 所有外部输入必须校验，是否使用 Zod 由当前复杂度决定；
4. 本地试用不引入完整 Auth，真实客户部署必须使用独立配置或最小访问控制；
5. V0.1 不要求数据库；若新增数据库表，必须包含 created_at；
6. 不因未来多租户预留而增加无实际用途的权限或组织代码；
7. 所有 AI 调用封装在统一 Provider 层；
8. 不允许在页面组件中直接调用模型；
9. 不允许在前端保存模型 Key；
10. AI 生成、审核和知识读取必须有明确的加载、成功和失败状态；
11. 所有 AI 输出必须保存 Prompt 版本和模型名；
12. 本地目录只读取支持的 Markdown、TXT；临时上传必须校验 MIME 和大小；
13. 关键流程必须提供错误提示；
14. 普通日志不得保存完整知识正文和模型敏感输入；
15. 知识连接器默认只读并使用最小权限；
16. 每完成一个模块，更新 README 和本 Spec 的实施状态；
17. 优先实现 P0，不提前开发 P1、P2；
18. 内容创作必须是默认首页，不再优先优化数据看板；
19. 四渠道生成必须基于统一内容简报和独立渠道 Prompt；
20. 插件只能采集当前浏览器有权限看到的页面信息，不实现绕过登录的爬虫；
21. 每次开始编码前先检查 PRD 的三个成功标准，无法直接服务这些标准的功能默认不做。

# 38. 最终产品判断

本项目第一阶段的核心，不是开发一个 SaaS、数据后台或“自动发内容的软件”。

核心是验证：

> 用户能否用自己的知识资料和一个选题，快速生成经过少量修改就能发布的多渠道内容。

第一版只通过三个结果判断：

1. 一组资料能生成四种渠道内容；
2. 内容经过少量修改即可发布；
3. 崔总愿意支付约 3000 元购买这项交付。

只有完成杏仁连续使用和崔总付费验证后，再继续开发爆款、草稿箱推送、发布复盘、多租户和付费系统。
